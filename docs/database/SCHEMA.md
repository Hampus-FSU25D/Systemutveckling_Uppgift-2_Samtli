# Samtli Database Schema

This document describes the authoritative relational model for the initial VG scope. The schema is defined by SQL migrations in `database/migrations/` and applied with `php bin/migrate.php`.

## Tables

### `users`

Stores registered Samtli users.

Important columns:

- `id` unsigned bigint primary key.
- `first_name`, `last_name` required names.
- `email` required unique email address, stored after later application normalization.
- `password_hash` required hash generated by PHP `password_hash(PASSWORD_DEFAULT)`.
- `created_at`, `updated_at` timestamps.

Constraints and indexes:

- `PRIMARY KEY (id)`
- `uq_users_email UNIQUE (email)`

Deletion behavior:

- Referenced users are restricted from deletion by authored or ownership records in the current VG scope.

### `groups`

Stores interest-based groups.

Important columns:

- `id` unsigned bigint primary key.
- `name` required group name.
- `description` optional long text description.
- `created_by` references the creating user.
- `created_at`, `updated_at` timestamps.

Relationships:

- `created_by -> users.id`

Constraints and indexes:

- `fk_groups_created_by`
- `idx_groups_created_by`

Deletion behavior:

- `created_by` uses `ON DELETE RESTRICT` so deleting a user cannot silently orphan group ownership.
- Records owned by a group cascade from `groups.id` in child tables.

### `group_memberships`

Stores per-group membership and role assignments.

Important columns:

- `group_id` references the group.
- `user_id` references the user.
- `role` is either `member` or `administrator`.
- `joined_at` records when the membership was created.

Relationships:

- `group_id -> groups.id`
- `user_id -> users.id`

Constraints and indexes:

- `PRIMARY KEY (group_id, user_id)` prevents duplicate memberships.
- `chk_group_memberships_role` allows only `member` and `administrator`.
- `fk_group_memberships_group`
- `fk_group_memberships_user`
- `idx_group_memberships_user` supports listing groups for a user.

Deletion behavior:

- Group deletion cascades memberships.
- User deletion is restricted while memberships exist.

### `group_join_requests`

Stores requests from users who want to join groups.

Important columns:

- `id` unsigned bigint primary key.
- `group_id` references the target group.
- `user_id` references the requesting user.
- `status` is `pending`, `approved`, or `rejected`.
- `created_at` records request creation.
- `handled_at` and `handled_by` are nullable until an administrator handles the request.

Relationships:

- `group_id -> groups.id`
- `user_id -> users.id`
- `handled_by -> users.id`

Constraints and indexes:

- `uq_group_join_requests_group_user UNIQUE (group_id, user_id)` prevents duplicate request rows.
- `chk_group_join_requests_status` allows only `pending`, `approved`, and `rejected`.
- `idx_group_join_requests_group_status` supports pending request lists per group.
- `idx_group_join_requests_user` supports user request lookups.
- `idx_group_join_requests_handled_by`

Deletion behavior:

- Group deletion cascades join requests.
- Requesting user deletion is restricted while requests exist.
- `handled_by` uses `ON DELETE SET NULL` so historical request records can remain if a handler account is removed in a future feature.

### `discussions`

Stores discussion topics inside groups.

Important columns:

- `id` unsigned bigint primary key.
- `group_id` references the owning group.
- `created_by` references the author.
- `subject` required topic subject.
- `created_at`, `updated_at` timestamps.

Relationships:

- `group_id -> groups.id`
- `created_by -> users.id`

Constraints and indexes:

- `fk_discussions_group`
- `fk_discussions_created_by`
- `idx_discussions_group_updated` supports listing discussions by group and activity/date.
- `idx_discussions_created_by`

Deletion behavior:

- Group deletion cascades discussions.
- Author deletion is restricted to preserve authored history.

### `posts`

Stores the first discussion post and all replies. There is no separate replies table.

Important columns:

- `id` unsigned bigint primary key.
- `discussion_id` references the discussion.
- `created_by` references the author.
- `content` required post body.
- `created_at`, `updated_at` timestamps.

Relationships:

- `discussion_id -> discussions.id`
- `created_by -> users.id`

Constraints and indexes:

- `fk_posts_discussion`
- `fk_posts_created_by`
- `idx_posts_discussion_created` supports chronological post listing.
- `idx_posts_created_by`

Deletion behavior:

- Discussion deletion cascades posts.
- Author deletion is restricted to preserve authored history.

### `group_invitations`

Stores single-use 24-hour group invitation links using token hashes only.

Important columns:

- `id` unsigned bigint primary key.
- `group_id` references the group.
- `created_by` references the administrator who created the invitation.
- `token_hash` is a unique lowercase hex SHA-256 hash of the raw token.
- `expires_at` is set by future application code to 24 hours after creation.
- `used_at`, `used_by` are nullable until redemption.
- `created_at` records creation.

Relationships:

- `group_id -> groups.id`
- `created_by -> users.id`
- `used_by -> users.id`

Constraints and indexes:

- `uq_group_invitations_token_hash UNIQUE (token_hash)`
- `idx_group_invitations_group` supports group invitation lists.
- `idx_group_invitations_created_by`
- `idx_group_invitations_used_by`
- `idx_group_invitations_expires_unused` supports unused/expiry checks.
- `fk_group_invitations_group`
- `fk_group_invitations_created_by`
- `fk_group_invitations_used_by`

Deletion behavior:

- Group deletion cascades invitations.
- Creator deletion is restricted while created invitations exist.
- `used_by` uses `ON DELETE SET NULL` so redeemed invitation records can remain if a redeemer account is removed in a future feature.

## Migration Tracking

The migrator manages `schema_migrations`.

Columns:

- `migration` primary key containing the migration filename.
- `applied_at` timestamp for successful application.

The runner creates this table automatically, sorts `database/migrations/*.sql` lexically, skips already-applied files, records each migration only after it executes successfully, and uses a MariaDB advisory lock to prevent concurrent migration runs.

## Database-Enforced Invariants

- User email addresses are unique.
- Foreign key targets must exist.
- A user can have at most one membership per group.
- Membership roles must be `member` or `administrator`.
- A user/group pair can have at most one join request row.
- Join request statuses must be `pending`, `approved`, or `rejected`.
- Invitation token hashes are unique.
- Raw invitation tokens are not represented in the schema.
- Group-owned memberships, join requests, discussions, and invitations cascade when a group is deleted.
- Posts cascade when their discussion is deleted.

## Application-Enforced Later

- Email normalization and validation before persistence.
- Password hashing during registration.
- Group creator receives an administrator membership in the same transaction as group creation.
- Only group members can read private discussions.
- Only group members can create discussions and posts.
- Discussion and first post are created transactionally.
- Only group administrators can approve or reject join requests.
- Only group administrators can create invitations.
- Invitation raw tokens are generated cryptographically securely.
- Invitations expire exactly 24 hours after creation.
- Invitation redemption is atomic and single-use under concurrent requests.
- Last-administrator safety if role management later requires it.
